# Локальные тесты

Из корня проекта:

```console
python run-tests.py
```

Скрипт без сторонних Python-библиотек подключает SDK **Cangjie 1.0.5** из
`C:\Program Files (x86)\Cangjie`, печатает версию компилятора, собирает актуальный
`main.exe` и проверяет его через **оригинальный `bench/interactor.exe`**.
PowerShell и установка пакетов через pip не нужны. При ошибке сборки старый бинарник
не запускается. Перед каждым тестом очищаются предыдущие результаты именно этого теста.

По умолчанию выполняются **все 65 тестов**:

- **1–15** — файлы организаторов в `bench/tests`, без изменений;
- **16–65** — дополнительные сценарии в `bench/extra-tests`, с весом 1.

Дополнительные тесты пересоздаются детерминированно при запуске из
`bench/generate_tests.py`. Править их вручную не нужно: для своего файла есть `--file`.
Описания сценариев, число операций, seed случайных генераторов и SHA-256 файлов
сохранены в `bench/extra-tests/manifest.json`.

## Команды

```console
python run-tests.py --suite official
python run-tests.py --suite extra
python run-tests.py --test 1 16 65
python run-tests.py --file my-test.in
python run-tests.py --no-build --test 1
python run-tests.py --generate-only
python run-tests.py --sdk "C:\Program Files (x86)\Cangjie" --timeout 30
```

`--no-build` явно запускает уже собранную программу; обычно этот флаг не нужен.
Номера дополнительных тестов 16–65 — **локальные обозначения**, они не связаны
с закрытыми тестами организаторов.

## Что проверяется

- Одиночные трубы длиной 1, 2, 19, 20, 21, 38, 39, 40; округление копания до 20 м.
- Повторяющиеся длины, возрастающие и убывающие последовательности, чередование
  коротких и длинных труб, точное заполнение траншеи.
- Освобождение соседних участков в разных порядках, слияние слева, справа и с обеих сторон.
- Полное освобождение и повторное заполнение; удаление в прямом, обратном и случайном порядке.
- Шахматная фрагментация, свободные начало, середина и конец траншеи.
- Большие свободные участки, разбиение остатков, переход через размер 40,
  удаление элементов из середины корзин одинакового размера.
- 12 случайных сценариев по 10000 операций с фиксированными seeds: разные длины,
  доли удалений от 10% до 95%, случайные и LIFO-удаления.
- 4 сценария по 200000 операций: рост до 8 млн метров, 100000 разных PID,
  два случайных стресс-теста.

Генератор отдельно проверяет допустимые длины, число команд и то, что удаляются
только существующие активные PID. Проверка размещения выполняется интерактором:
трубы должны находиться в траншее, не пересекаться; при удалении требуется верная позиция.
Нулевая заполненность в конце допустима: **KPI=0 может быть успешным тестом**.
Заведомо некорректные входные команды в набор не включены: организаторы их не обещают.

## Результаты

Каждая строка содержит статус, название сценария, число операций, KPI, баллы,
реальное время, процессорное время и пик рабочего набора памяти процесса решения.

```text
KPI = длина оставшихся труб / длина траншеи
score = KPI * вес теста
```

`Official score` суммирует только выбранные открытые тесты; для всех 15 сумма весов — 32.1.
Дополнительные сценарии имеют отдельную сводку с долей успешных проверок и средним/минимальным
KPI. Их баллы не добавляются к соревновательному результату. Малый KPI на одиночной
короткой трубе ожидаем: 1 метр на минимальной траншее 20 метров даёт 0.05.

На Windows CPU-время и память считываются через системный API без `psutil`.
Превышение 5 CPU-секунд или 256 MiB пикового рабочего набора отмечается отдельным статусом.
Это локальная оценка ресурсов; машина и способ учёта памяти у организаторов могут отличаться.
`--timeout` — отдельный предел **реального времени** для пары решение+интерактор,
по умолчанию 30 секунд: он ловит зависание и отсутствие flush, а не имитирует CPU-лимит.
На тяжёлых тестах интерактор тоже тратит время на обработку 200000 обменов.

Ошибки дают ненулевой код завершения скрипта. Для каждого теста остаются:

```text
target/test-results/official/1/
target/test-results/extra/65/
  answer.txt
  score.txt
  report.txt
  interactor.stderr.txt
  solution.stderr.txt
target/test-results/summary.json
```

`summary.json` обновляется после каждого теста и содержит также длины траншеи и
оставшихся труб. Логи разных тестов хранятся отдельно; повторный запуск теста заменяет его логи.

Проверить сам тестовый запуск (падение, неверный ответ, таймаут, отсутствие перевода
строки, устаревшие баллы, допустимый нулевой KPI и воспроизводимость генератора):

```console
python bench/test_harness.py
```

Этот набор покрывает разнообразные граничные и нагрузочные случаи, но конечный
набор тестов не гарантирует отсутствие всех ошибок или высокий KPI на неизвестных
закрытых сценариях. Для поиска новых ошибок можно добавлять профили и seeds в генератор.

## Сравнение online-эвристик и риска подгонки

```console
python -m unittest bench.test_compare_online
python bench/compare_online.py --count 400
python bench/compare_online.py --count 800 --start 720000 --diverse --variants baseline churn-left high-churn-left diverse-left
python bench/compare_online.py --count 100 --prefix-probes --variants baseline
```

`bench/compare_online.py` компилирует отдельные бинарники в `target/online-comparison`,
не меняя `src/main.cj` и основной `target/release/bin/main.exe`. `--source` позволяет
проверить отдельный снимок исходника, `--output` задаёт отдельный каталог результатов.
В `results.json` сохраняются KPI и длина траншеи каждого сценария для попарного сравнения.
Дополнительно всегда проверяются 15 официальных и 50 дополнительных файлов.

`--prefix-probes` дописывает новые допустимые продолжения к префиксам официальных
тестов. Это важная проверка риска предвычисленных размещений: корректный переход на
online-аллокатор не возвращает уже выкопанную лишнюю траншею.
`--diverse` добавляет независимые случайные алфавиты длин, доли и порядки удалений.
Это уменьшает зависимость выводов от корреляций в 20 семействах massive-генератора.

Проверяются все размещения, границы траншеи, непересечение, позиции удаления,
число ответов и код завершения. Это **не интерактивный** запуск: ресурсные лимиты,
flush и протокол нужно дополнительно проверять `run-tests.py`.
Поле `bound` — верхняя граница KPI по пику суммарной длины живых труб; оно не является
доказанным достижимым оптимумом размещения неподвижных труб.
