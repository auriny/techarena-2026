# TechArena 2026 — Service Zone Optimization

Аналитическая записка по условию (как его проверяет `validate_solution.py` и README посылки) и по тому, где текущий солвер теряет ОПЗ.

Источники: `data/samples/README.md`, `data/validate_solution.py`, фактическое поведение `Main.java`, таблица NSUTS.

---

## 1. Что это за задача

Нужно открыть несколько сервисных офисов, назначить им объекты (`sites`) и специалистов (`workers`), чтобы **максимизировать** денежную цель при жёстких ограничениях.

Это не «просто кластеризация». Три решения связаны:

1. **какие офисы открыть** (дискретное подмножество);
2. **какие объекты отдать каждому** (разбиение с геометрией);
3. **каких работников посадить в каждый открытый офис** (покрытие навыков).

Пустое решение допустимо и даёт цель `0`. Невалидное решение на NSUTS — Wrong Answer, балл за тест обнуляется.

### Контракт тура

| Параметр | Значение |
|---|---|
| Вход | `instance.json` в текущем каталоге |
| Выход | только `solution.json` |
| stdout | молчать |
| Лимит | ~5 мин и 8 ГиБ на тест |
| T на практике | **процессорное** время процесса (сумма потоков), не wall×ядра |
| Посылка | один `Main.java`, обученный файл весов передать нельзя |

ОПЗ в рейтинге — нормировка сырых целей относительно **лучшего известного** результата по каждому тесту. Быть «на своём потолке» ≠ быть на 0.99 от лидера.

## 2. Формат данных

### `instance.json`

- **`sites[i]`**: `(x, y, reward, tasks[])`. `tasks` — типы работ (навыки), индексация с нуля. На одном объекте задач может быть несколько, в том числе с повтором: в цели дисбаланс считается как `len(tasks)`, не как число уникальных навыков.
- **`offices[j]`**: `(x, y, cost, maxSize)`. `cost` платится **за факт открытия**, независимо от числа объектов. `maxSize` — максимум назначенных объектов.
- **`workers[w]`**: список навыков специалиста.
- **`distances[j][i]`**: стоимость пути офис `j` → объект `i`. Это **не евклидово** расстояние. Евклид на `(x,y)` нужен только оболочкам.
- **`maxDifference`**: жёсткий лимит на разницу **числа объектов** между любой парой открытых офисов.
- **`balanceCoefficient` (α)**: коэффициент мягкого штрафа за разницу **числа задач**, не объектов.

### `solution.json`

Массив открытых офисов:

```json
{ "officeId": 0, "sites": [1, 4], "workers": [0, 2] }
```

Индексы с нуля. Объект и работник не могут входить в два офиса.

## 3. Целевая функция

Для валидного решения:

```
objective = Σ reward(s)
          − Σ distances[office(s)][s]
          − Σ cost(открытый офис)
          − α · (maxTasks − minTasks)
```

где `tasks(офис) = сумма len(sites[s].tasks)` по его объектам.

Следствия:

- Необслуживаемый объект даёт **ноль**, а не штраф. Если `reward − dist` мало или объект ломает оболочку, его выгоднее бросить.
- Открытие офиса окупается только если пойманный `Σ(reward − dist)` плюс эффект α больше `cost`.
- При большом α выгоднее **выровнять нагрузку по задачам** или открыть один офис, чем набрать больше reward неровно.
- `maxDifference` режет по **количеству объектов**. Можно иметь 5 и 7 объектов при `maxDifference = 2`, но 40 и 80 задач — это уже только штраф α, если оба офиса открыты.
- Матрица `distances` может быть сильно неевклидовой. Кластеризация по `(x,y)` и кластеризация по дороге — разные назначения.

Верхняя оценка (недостижимая): сумма положительных `(reward[s] − min_j distances[j][s])` минус минимальная стоимость офисов, которые вообще могут их взять, без оболочек и α. На скрытых тестах до этой оценки мы, скорее всего, далеко: режет геометрия, не арифметика.

## 4. Ограничения (как в валидаторе)

Проверка идёт строго в этом порядке. Любая ошибка — весь тест = 0.

1. **Индексы и уникальность.** Офис / объект / работник в пределах массивов, без повторов.
2. **Ёмкость.** `|sites(офис)| ≤ maxSize`.
3. **Баланс объектов.** Для любой пары открытых офисов `|n_i − n_j| ≤ maxDifference`. Пустой офис в решении лучше не держать: он даёт `n = 0` и часто ломает баланс.
4. **Навыки.** Каждая задача каждого объекта офиса покрыта **хотя бы одним** работником этого же офиса. Глобальный пул навыков делится между офисами: редкий навык нельзя отдать двум зонам сразу.
5. **Геометрия зон (главный жёсткий фильтр).**  
   Для офиса берётся множество точек: **его координата + координаты его объектов**. Строится выпуклая оболочка (shapely `MultiPoint.convex_hull`, `covers` с границей).  
   Точки, которые оболочка покрывает, — **все объекты и все офисы инстанса**, включая неоткрытые и неназначенные.  
   Две открытые зоны **не имеют права покрывать одну и ту же точку**.

Важные следствия геометрии:

- Оболочка зоны A может накрывать чужой **неназначенный** объект. Это само по себе не ошибка. Ошибка — если та же точка лежит и в оболочке зоны B.
- Офис, который попал внутрь чужой оболочки, тоже конфликт. Нельзя «обложить» соседа своими объектами так, чтобы его здание оказалось внутри.
- Одна точка + офис → отрезок. Любой объект/офис на этом отрезке считается покрытым. Две почти коллинеарные зоны легко конфликтуют.
- Три точки с большой площадью «съедают» пространство между ними. Жадное добавление дальнего жирного объекта часто убивает десяток средних.
- Это **не** disjoint polygons только по назначенным точкам. Это disjoint **covers** на полном наборе точек карты.

Именно поэтому Вороной по евклиду систематически врёт: он режет плоскость по ближайшему офису, а валидатор смотрит на выпуклые оболочки, которые залезают в чужие ячейки.

## 5. Как устроен текущий солвер

Два этажа, которые нельзя смешивать по CPU.

### Этаж A — поиск набора офисов (cheap)

Дешёвая сборка: евклидов Вороной → навыки concentrate → `improve` в одном режиме → `finalize` (работники, баланс объектов, починка оболочек выкидыванием точек).

На больших картах перебираются в основном `k = 2, 3`, плюс окно вокруг `predictK`, соседи, random. На малых (`nOff ≤ 8`) — все маски.

Скорер набора — residual MLP (линейный RankNet + 8 ReLU) с зашитым приором. Он **не назначает объекты**. Он говорит, какой набор офисов стоит посчитать.

### Этаж B — назначение (thorough)

На элитных наборах: дорожная матрица, несколько политик навыков, leftover (прямой и парный add против α), на compact ещё polish / hull-grow.

`finalize` в конце может **снять** уже найденные объекты: нехватка работников, `maxDifference`, конфликт оболочек. Это скрытая потеря цели, которую поиск по cheap не видит.

### Что эмпирика NSUTS уже доказала

| Наблюдение | Вывод |
|---|---|
| OPZ 7.5 при дешёвом поиске k=2/3 и одном thorough | На больших скрытых тестах узкое место — **набор офисов**, не полировка |
| OPZ 4.2 при пуле ядер и thorough на всех парах | T = CPU процесса; многопоток и тяжёлые сборки **съедают** перебор |
| 12.46M на тесте 5 vs 12.10M после «улучшения» assignment | Другой набор k=2 лучше, чем более красивое назначение неправильных офисов |
| 203k → 172k на тесте 8 | Средние карты недобирают **thorough assignment** |
| Локальные 1000/1000 vs свой оракул | Карты `nOff ≤ 6` не моделируют скрытые; это самопроверка, не оценка ОПЗ |
| Тесты 1–4, 6, 7, 10 почти не двигаются между посылками | Либо потолок уже рядом, либо все наши версии делают одну и ту же ошибку одного класса |

ОПЗ ~7.2 из 11 значит: в среднем ~66% от **текущего лучшего на тесте**, не от теоретического оптимума. Чтобы на каждом тесте было ≥ 0.99, нужна сумма отношений ≈ 10.9.

## 6. Где лежит разрыв до 0.99

Разрыв почти наверняка **неравномерный**. Три разных класса тестов.

### Класс L — крупные (похоже, 5 и 11, возможно 1)

Много объектов, офисов больше 8. Полный перебор `2^{nOff}` не влезает. Cheap-оценка набора и thorough-оценка **расходятся**: leftover и оболочки меняют цель на миллионы. Если модель и `consider()` выбирают победителя по cheap, thorough уже не спасёт чужой набор.

Что улучшить:

- Считать **маргинал офиса**: сколько leftover после текущего решения он может забрать без конфликта оболочек. Это add/drop в пространстве офисов, а не random k.
- Не ранжировать наборы по cheap-obj. Ранжировать по `cheap + прогноз leftover/hull-gap` (это как раз роль MLP, но метка должна быть thorough, и дешёвых меток в SGD должно быть меньше).
- Large Neighborhood Search по офисам: выкинуть 1–2 офиса, заново назначить, вернуть лучших. Сейчас есть только swap соседа.
- Не тратить `C(n,4)` и `C(n,5)` раньше, чем закрыты все пары. Пары уже выигрывали тест 5.

### Класс M — средние (похоже, 8 и 9)

`nOff` небольшой, полный cheap по маскам реален, а полный thorough — нет (TLE на тесте 9 при thorough всех масок `nOff = 8`). Потолок упирается в назначение: сколько объектов удаётся удержать в непересекающихся оболочках.

Что улучшить:

- **Растить зоны от офиса**, а не резать Вороным и чинить. Каждый следующий объект — тот, чей прирост `reward − dist − Δα` максимален при условии, что новая оболочка не пересекается с уже открытыми covers.
- Ruin-and-recreate: снять 10–20% объектов (особенно вершины оболочек — они определяют площадь), вставить leftover.
- Не выкидывать вершину оболочки первой при `maxDifference`: выкидывание внутренней точки площадь почти не меняет, выкидывание вершины может освободить чужой leftover.
- Парный обмен объектами между офисами с проверкой оболочек (уже есть `swapBest`, но только на compact). На классе M его нужно успевать всегда.

### Класс S — мелкие (6, 9?, 10)

Мало объектов. Здесь должен работать полный перебор наборов + несколько политик назначения. Если мы не на 0.99, либо α/навыки режут неочевидно, либо `finalize` ломает оптимум выкидыванием «худшего» объекта вместо другого.

Что улучшить:

- На tiny не обрывать поиск дедлайном (уже так).
- Перебор не только наборов офисов, но и **перестановок навыков**, если навыков мало.
- Несколько seed у `buildBalanced`.

### Общее, что сейчас сделано слабо

**Работники почти не оптимизируются.** `allocateWorkers` — покрытие нужд офиса из глобального пула. Редкий навык, отданный слабому офису, может запретить сильный leftover у другого. Имеет смысл: сначала назначить объекты, потом **перекидывать** работников с уникальным навыком туда, где они открывают добавление объекта.

**`finalize` разрушает цель.** Любой improve/leftover бессмыслен, если потом `repairGeometry` / `enforceSiteBalance` снимает лучшие точки. Нужен repair, который снимает **минимальный конфликтный набор** (вершины overlapping region), а не «первый попавшийся / худший value».

**Евклид vs дорога.** Поиск офисов живёт в евклидовом Вороном. Если скрытая дорожная матрица — сильный объезд, офис «рядом на карте» дорогой. Thorough смотрит дорогу слишком поздно.

**α считается по задачам, баланс — по объектам.** Политики, которые выравнивают `|sites|`, могут разъезжать по `tasks`. Нужен явный шаг: перенос объекта с большим `len(tasks)` из max-офиса в min-офис, если оболочка позволяет.

## 7. Что не надо делать (уже обожглись)

1. **Много потоков.** T суммирует CPU. 8 ядер × 200 с wall ≈ TLE.
2. **Thorough на всём поиске.** Красивое назначение неправильного набора хуже грубого назначения правильного.
3. **Нейросеть вместо construct.** Назначение — комбинаторика с дискретными оболочками; сеть это ломает и просаживает 5/11.
4. **Обучение на своих мелких тестах.** Оракул = тот же солвер на `nOff ≤ 6`. Модель выучивает «маленький k и cheap-obj».
5. **Полный thorough всех масок при `nOff = 8` и большой карте.** Тест 9 уходит в T.
6. **Игнорировать дедлайн только на средних картах.** Tiny — да. Compact/large — нет.
7. **Считать ОПЗ относительно своей старой посылки.** Соперники поднимают знаменатель. 7.5 мог стать 7.2 без деградации наших сырых баллов, и наоборот.

## 8. Приоритеты: что даст ОПЗ, а что нет

По ожидаемому эффекту на скрытых тестах, не по красоте кода.

### P0 — назначение как упаковка оболочек

Перестать думать «кластер → починить геометрию». Думать «упаковать k непересекающихся covers максимального `Σ(reward − dist)`».

Конкретно:

- рост зоны от точки офиса с проверкой `covers` на каждом шаге;
- при конфликте пробовать **другую вершину**, не бросать весь объект в leftover навсегда;
- LNS: разрушить оболочку (снять 2–4 крайние точки), заполнить leftover;
- repair геометрии через минимальный vertex cut overlapping region.

Это бьёт класс M (тесты 8/9) и leftover на классе L.

### P1 — поиск офисов по маргиналу, не по сумме одиночных

Одиночная сборка офиса завышает тех, кто «забирает всю карту себе». В паре они конфликтуют оболочками.

Конкретно:

- greedy: начать с лучшего одиночного, добавлять офис с максимальным **приростом thorough или hull-grow** на leftover;
- drop: закрыть офис, если его объекты дешево переезжают;
- не больше одного полного прохода k=4, пока не исчерпаны пары.

Это бьёт класс L (5/11).

### P2 — работники как ключ к leftover

После фиксации объектов: для каждого leftover с уникальным навыком посмотреть, можно ли пересадить единственного носителя навыка в офис, который геометрически может взять этот объект.

Сейчас навыки назначаются **до** leftover и почти не пересматриваются.

### P3 — модель

Residual MLP уместен только как **суррогат thorough-цели набора**. Он не должен:

- управлять назначением объектов;
- учиться на cheap-метках мелких карт как на основной лосс.

Имеет смысл:

- на скрытом тесте копить пары `(набор, cheap, thorough)` и учить **зазор** `thorough − cheap`;
- в очереди thorough брать top по `cheap + predicted_gap`, не top по cheap;
- оффлайн-fit только на картах с `nOff ≥ 8` и пересекающимися оболочками (`LocalSuite hard` / `fit`).

Сменить MLP на бустинг/граф нельзя: в посылку не положить файл, а 241 вес ещё влезает в исходник.

### P4 — тесты

Старые 1000 штук оставить как регрессию валидности. Для качества:

- жёсткие: 80–200 карт, `nOff 8–15`, `nSites 50–180`, офисы в центре облака, кольца, далёкие кластеры, высокий α, один редкий навык;
- метрика не «совпали с оракулом», а **доля leftover reward** и **число конфликтов оболочек до repair**;
- отдельный прогон: cheap-победитель vs thorough-победитель на одном инстансе — если часто разные наборы, модель и `consider()` смотрят не туда.

## 9. Как смотреть на один скрытый тест

Без инстанса можно только гадать. Если появится лог / open-пакет большего размера, смотреть в таком порядке:

1. Сколько объектов из всех попало в ответ? Если `< 70%` при свободной ёмкости — это оболочки или навыки, не k.
2. `Σ(reward − dist)` vs `α · imbalance`. Если штраф α того же порядка, что недобор reward, выравнивать задачи, не открывать лишний офис.
3. Открыто k=1 при `nOff > 10`? Либо opening cost огромный, либо `predictK` рано остановился, либо пары дешёвой сборкой выглядят хуже одиночки (типичный баг Voronoi+hull).
4. Есть ли leftover с `reward − dist > 0` рядом с офисом, но вне оболочки? Это вершина чужой зоны. Снимать вершину, не давить leftover в ту же оболочку.
5. CPU: сколько наборов успели cheap vs сколько thorough. Если thorough > 20 на большой карте — снова съели поиск.

## 10. Вывод аналитика

Задача — **max-weight packing непересекающихся выпуклых зон** с побочными knapsack (ёмкость, навыки) и двумя разными балансами (жёсткий по объектам, мягкий по задачам). Дорога задана матрицей, геометрия — евклидом. Это два пространства, и солвер живёт в основном в евклидовом.

Текущий код уже умеет выдавать валидные решения и держать большой дешёвый поиск — поэтому тесты 1–4/6/7/10 стоят, а 5/11 чувствительны к объёму пар. Дальше «ещё чуть-чуть polish / ещё чуть-чуть SGD на мелких тестах» ОПЗ не поднимет.

Чтобы приблизиться к 0.99 на каждом тесте, менять нужно **порядок решений**:

1. непересекающиеся оболочки как первичный объект оптимизации;
2. набор офисов по маргиналу leftover, не по сумме одиночных cheap;
3. работники как средство открыть leftover, не как хвост `finalize`;
4. модель только как предсказатель зазора cheap→thorough на больших картах.

Пока назначение чинит Вороной, а поиск верит cheap-цели, потолок будет около «своего 7.x», сколько бы локальных тестов ни сходилось в 1000/1000.
